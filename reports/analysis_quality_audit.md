### 3.3 `_edges.json` vs `_edges_full.json`：哪个是陈旧的

两者由**两个不同版本/不同作者的边抽取器**产生（`classify.py` 与 `build_graph.py`），互不兼容：

| | `_edges.json`（classify） | `_edges_full.json`（build_graph） |
|---|---|---|
| 边数 | 143 | 128 |
| 唯一 (source, target) | 110 | 109 |
| 字段 | `source_swf,target,api,location,evidence,confidence,note` | `source,target_pattern,api,location,evidence,confidence,resolved_target,note` |
| 置信度词表 | CONFIRMED / LIKELY / INFERRED | CONFIRMED / PATTERN / MISSING / INFERRED |
| 分布 | CONFIRMED 0, LIKELY 7, INFERRED 136 | CONFIRMED 4, PATTERN 8, MISSING 11, INFERRED 105 |

**判定：`dependency_edges.csv` 与 `_edges.json` 同代（非陈旧），`_edges_full.json` 与磁盘上的 CSV 不同代。** 依据：磁盘 CSV 的表头与 `_edges.json` 的字段集逐列一致、行数同为 143；且 `README.md:92-96` 的顺序让 `build_graph` 在 `classify` **之后**运行，若真按 README 跑过，最终留在盘上的应是 `_edges_full.json` 那一版。**结论：README 的复现顺序与仓库里的提交产物互相矛盾**，实际生成顺序必然是 build_graph 先、classify 后。

## 7. 第 8 项：清单可追溯性

**问题**：`analysis/<id>/metadata.json` 由 `jpexs_batch.py:264` 从 `swf_struct.analyze()` 的记录直接 `dict(rec)` 复制而来，**记录了 sha256 但从不校验**。也就是说它是一个"当时的快照"，没有任何机制在后续使用时（`build_inventory.py`、`classify.py`、`build_graph.py`）回头核对输入文件是否还是那一个。

**实测结果：14 个 `kofwing` 文件中 5 个对不上**（见 B1）。其中最关键的是主程序：

```
_struct.json / metadata.json 记:  125,450,217 B  sha256 319fb968de79…
磁盘实际 (kofwing/21256864.swf):  125,442,502 B  sha256 847a0ec9febb…
差值:                                    -7,715 B
```

`reports/recovery_manifest.json:47-55` 给出了完整解释：该文件被 `recover_from_exe.py` 从 EXE 按偏移 21,256,864 重新切出时**在 EOF 处被截断**（`truncated_at_eof: true`）——即 EXE 里剩下的字节比初版提取物少 7,715 字节。

**影响**：`file_inventory.csv` 里 `kofwing/21256864.swf` 的 `sha256` 与 `bytes` 两列**都指向一个已不存在的文件**。任何以该 CSV 为准的校验、补丁或二次恢复都会失败。另 4 个被拒文件的 sha256 同样失配（大小未变、内容已变）。

**一个反向的好消息**：仓库里 `experiments/work/orig.swf` 的 sha256 = `847a0ec9febb…`，与当前磁盘版本**完全一致**。也就是说当前在用的主程序副本至少还有第二处留存，可以互相印证。

**建议**：`build_inventory.py` 在拼表时对每个 `valid_swf` 记录重新计算输入 sha256 并与 `_struct.json` 比对，不一致就单独出一列 `input_sha256_match`，让漂移可见而不是沉默。
